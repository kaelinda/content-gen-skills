# Writing Koubo Scripts

从已定稿的文字简报，改写成适合朗读和语音合成的中文口播稿。本技能只负责文稿，不负责调用 TTS、发频道或上传播客。没有文字底稿时，先整理或向调用方索取，不要凭空编新闻。

## Input

调用方应提供：

- 已定稿的文字简报，或等价要点
- 节目口头称呼（书面名和口头名不同时，口播稿只写口头名，让 TTS 按字朗读）
- 目标时长（默认大约 3–6 分钟）
- 开场、收束是否有固定句式

口播稿必须能从底稿和原始出处核对。不要新增底稿里没有、出处也无法支持的事实、数据和评价。

## Script structure

常见结构（调用方另有指定时以指定为准）：

1. 开场：问候、节目口头称呼、日期（用口语，如「十一月十日」）
2. 今日主线：1–3 句，概括当天最值得先听的线
3. 分节：按主题读出简短节名（如「iOS。」「模型。」）；某节没有内容就整节不写
4. 收束：固定结束语（如有）；指向文字版所在渠道时只说名称，不念网址

## One item, one beat

常见问题是：同一节里多条资讯用「另外」「同时」「则」粘在一段里，语音合成会连着读，听感上没有分割。

写的时候：

- 一条资讯单独成段，段与段之间空一行
- 先说清楚事实，再跟一到两句短评，然后结束本段；下一条另起一段
- 不要用「另外」「同时」「还有」把下一条接进同一段
- 节名单独成段，或放在该节第一条之前；节与节之间也空一行
- 不要把文字版里给后续选题用的「点评：可写《…》」读出来

不要臆造停顿标签、SSML 或特定厂商的 break 语法，除非调用方确认当前语音引擎支持并给出写法。靠分段、完整句号和一条一评来形成停顿。

## Commentary after each item

每条资讯在事实之后，补一到两句简短分析或评论，帮助听者判断，而不是只报事实。优先使用已经采到的材料，按可用性选一种，不要堆砌：

- 网友或社区里反复出现的反应（来自评论、引用或跟帖）
- 相关领域从业者或原作者的判断
- 对听者有用的走势或用法：该不该马上跟、还缺什么、和近期同类消息怎么放在一起看

硬性限制：

- 评论必须有出处。没有可靠来源时，不要编造「网友说」「某大佬认为」「社区普遍觉得」
- 出处不够时，可以用一句谨慎的用法提醒，且必须是底稿或官方材料已经支持的，例如「官方还没正式发布，先当路由传闻」「付款批准还在路线图上，现在不适合当日常默认」
- 仍然没有可说的判断，就只把事实说完并分段，不要硬凑点评
- 不要把未证实的时间表或评测分数说成定论；不确定就标明是传闻或尚未确认
- 短评是判断，不是口号，也不要写成广告腔

如果加上短评后可能超时，优先压缩事实里的次要数字和并列列举，而不是删掉有出处的短评，或把多条重新黏回一段。

## Spoken style

- 写出来的字就是将要被读出来的字。用口语完整句，不用 Markdown、列表符号、粗体、链接或 @用户名
- 版本号、漏洞编号、日期、金额、百分比写成中文口语，如「二十七点二点一」「百分之三十」；不要在口播里堆一长串对照版本，只保留听者需要执行的那个
- 英文专有名词保留通用读法，不要把品牌书面名按字母逐个念；若调用方规定了口头名，全文统一用口头名
- 少用破折号和括号补充；需要补充时改写成独立短句
- 不要套话和排比口号

## Workflow

1. 先读完文字底稿，划出条目、可引用的评论，以及不能上口播的网址、选题点评和按规则应省略的细节
2. 写开场和今日主线
3. 逐条改写：一段一事，事实加短评，空行分隔
4. 通读一遍：检查是否还有段内粘连、无出处评价、书面标题腔、过长版本清单
5. 按目标时长删减次要事实；输出纯文本口播稿，不要夹私人备注

## Example

欠佳（两条粘在一段里，也没有判断）：

> 苹果推送了二十七点二点一。另外，有人发布了可在手机上本地跑助手的应用。

更好：

> 苹果已推送二十七点二点一，主要是修错误和安全补丁。这是跟进更新，当天有旧设备的，优先确认有没有打上。
>
> 有应用宣称可以在手机上本地跑助手，不必越狱。官方文档写明，屏幕内容会发给你配置的模型，付款批准还在路线图上，现在更适合当试验，不适合当成日常默认。

## Common mistakes

- 整节写成一大段，条与条之间没有空行
- 用「另外」「同时」把下一条粘在上一句后面
- 只有事实，没有判断；或为了有评论而编造网友和从业者的话
- 把文字版的选题点评直接念出来
- 在口播里念网址、Markdown 或 @用户名
- 臆造语音停顿标签
- 脱离底稿补充新闻
